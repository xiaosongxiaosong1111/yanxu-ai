## 1. 分工与检查流程

1. Codex 给本机 Claude 下发一个节点：目标、允许修改范围、现有边界、失败用例与验收条件。
2. Claude 先读调用方，再写失败回归、完成实现和定向检查；仅完成当前节点，不自行进入后续节点。
3. Claude 返回结构化报告及真实日志，状态为 `submitted_for_review`，不能自行标记 Codex 验收通过。
4. Codex 检查实际 diff、调用方、数据影响及红绿测试证据，独立执行必要回归，给出 `passed` 或 `changes_required`。
5. 需要返工时把具体问题发回本节点；通过后才下发下一节点。代码实施与用户实际效果分别验收。

结果通过当前运行中的 Claude CLI 进程返回，并保存节点报告。它不等于 Claude 能向任意 Codex 对话主动发送消息：当前运行结束或对话中断后，后续协作通过保存的会话/节点记录恢复，重新核对结果后继续。

只读预检用于验证 CLI 可用、任务包可读和报告可回传；预检通过不等于代码节点完成。节点1、3由Codex接手的例外均获用户明确授权，后续节点仍按上述分工推进。

## 3. 向量后端方向：优先验证 Milvus

建议数据分工：SQLite 保存正文、片段、来源、审校、版本和索引任务；Milvus 保存片段向量与必要的过滤字段；原始文件独立按 SHA 留档；Embedding 服务负责生成向量。

### 节点4先检查环境，再选择运行模式

- 首先验证 Milvus Lite 能否在隔离环境运行。官方当前文档列出 Windows，但要求兼容的依赖 wheel；本项目 Windows/Python 环境是否满足，尚未实际安装验证。
- 如果本地 Lite 兼容性或目标能力不满足，再评估 Docker Desktop/WSL2 上的 Standalone；先确认本机资源、已有容器和端口，保持其他项目服务不受影响。
- 不同时维护多套向量后端，不在节点1安装 Milvus、启动容器或迁移现有数据库。
- 实际部署时重新核对官方兼容说明并锁定 SDK/服务版本，不能假设 Lite 与 Standalone 的所有能力和存储格式相同。

### 节点4必须通过的最小验证

1. 新建隔离集合，使用测试向量完成写入、过滤检索与读取；固定向量只证明存储接口。
2. 通过实际 Embedding 服务验证片段与查询生成，区分真实模型验证和固定向量夹具。
3. 学校、年度、质量和可见范围在截取结果前过滤，返回前再次核对 SQLite 的当前有效状态。
4. 进程或服务重启后数据可用；失败任务可幂等重试；来源撤信后残留向量不能成为可信结果。
5. 向量索引可由原文/片段及版本信息重建，更换模型或维度采用新代次验证后切换。
6. 不含私人对话、用户档案或 Key；增量建索引和查询调用有用量记录，不重复向量化整库。

参考：[Milvus Lite 官方说明](https://milvus.io/docs/milvus_lite.md)、[Standalone 部署](https://milvus.io/docs/install_standalone-docker.md)、[标量过滤](https://milvus.io/docs/boolean.md)。参考机制不代表本机已验证兼容。
